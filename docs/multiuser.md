# Многопользовательские подписки

## Границы ответственности

Сбор, фильтры и дедупликация выполняются один раз, независимо от числа подписчиков.
`seen_items` содержит публикации, полный payload и `eligible_at` — границу цикла,
из которого событие разрешено рассылать. Старые поля доставки остаются для аудита
и совместимости инструментов прежней версии. Их нельзя использовать для оценки
текущей персональной очереди.

`users`: `telegram_id` (PK), nullable `username`, `is_active`, `created_at`,
`updated_at`, `subscribed_at` (UTC Unix time). Повторный активный `/start` сохраняет
границу подписки. Возобновление после `/stop` устанавливает новую границу.

`user_deliveries`: `id` (PK), `telegram_id`, `item_key`, `status`, `attempts`,
`available_at`, `sent_at`, `telegram_message_id`, `reason`; уникальность пары
`(telegram_id,item_key)`, внешние ключи и индексы для очереди/статуса пользователя.

Состояния: `pending → sending → sent | pending | uncertain | failed`.
Задачи недоступных источников переходят в `suspended`, освобождая активную очередь.
После успешного свежего сбора они возвращаются в `pending` порциями и с сохранением
попыток и времени следующего повтора. `sending` не приостанавливается.
Перед HTTP атомарно увеличивается attempts и сохраняется `sending`. Сбой процесса
оставляет доставку в `uncertain` при следующем открытии БД. Сетевой результат,
который нельзя достоверно определить, автоматически не повторяется. `expired`
означает потерю актуальности, `skipped` — паузу или отключённый источник;
`legacy_review` требует разбора старой очереди. Все состояния независимы по адресатам.

403 отключает только адресата и отменяет его `pending` и `suspended`. 401 завершает процесс.
429 устанавливает общую паузу по `retry_after`. ConnectTimeout откладывает только
задачу с экспоненциальной задержкой до часа. Остальные ошибки сети и 5xx считаются
неопределёнными. Между попытками действует общий интервал 1,1 секунды; основной
цикл проверяет очередь раз в две секунды. Проверка публикации и текущих правил
перед отправкой сохранена. Неисправный источник не делает событие отправляемым.

Ответы на команды сохраняются в `command_replies` вместе с offset и изменением
подписки: во время 429 приветствие остаётся отложенным. На чат хранится последний
ответ; новая команда заменяет предыдущий. Очередь ограничена 1000 ожидающими чатами
(при переполнении вытесняется самый старый ответ, состояние подписки сохраняется).
`sending` после перезапуска становится `uncertain`; неоднозначный ответ не повторяется.
Получить актуальный статус можно новой командой `/status`.

Ответы на публичные команды отправляет общий планировщик, а не poller. При наличии
готовых событий и ответов HTTP-попытки чередуются. Ошибка, повтор или неопределённый
исход тоже занимают один ход; общий `send_after` и 429 соблюдаются обеими очередями.
Если готова лишь одна очередь, она использует свободные ходы. Итог административного
`/check` также проходит как служебная отправка.

На пользователя допускается не более одной попытки ответа в пять секунд. Повторные
команды заменяют ожидающий текст последним ответом; `/start` и `/stop` сохраняют
состояние сразу независимо от ограничения ответа. В `command_reply_limits` хранится
`telegram_id` и ближайшее разрешённое время, поэтому перезапуск лимит не сбрасывает.
Истёкшие записи очищаются при следующем claim; подписки от этого не меняются.

## Подписка без архива

Подписчик получает только события с границей цикла не раньше своей активации;
для впервые найденной публикации известная дата также должна быть позже активации. Подписавшийся
во время HTTP-сбора не получает текущий пакет. Первый снимок нового источника
остаётся общим baseline. Для публикаций без даты граница берётся из предыдущего
успешного снимка источника: первый снимок после подписки/возобновления также
не рассылается. Это осознанно может пропустить новое событие из такого снимка,
чтобы исключить выдачу неизвестного архива. Ошибка источника baseline не продвигает.

Ожидающие задачи создаются порциями до 500; одновременно не более 10 000
`pending`/`sending`. Недоступные источники не получают новых задач, а их существующие
задачи приостанавливаются без потери истории. Места распределяются порциями между
доступными источниками; при недостатке мест порядок источников меняется по кругу.
Отключённые источники получают `skipped`; `/stop` отменяет и приостановленные задачи.
При освобождении места недостающие задачи восстанавливаются
из сохранённых границ событий и подписок. История не удаляется. Возобновление
не создаёт задач из периода паузы. Просмотр очереди ограничен 100 строками за проход,
с продвижением курсора, чтобы неисправный источник не задерживал другие источники.
SQLite и последовательная отправка рассчитаны на умеренную аудиторию; при росте
числа пользователей увеличиваются задержка рассылки и объём истории на диске.
При нехватке места сбор/отправка требуют вмешательства оператора.

## Миграция и диагностика

Существующая база резервируется SQLite backup API до изменения схемы в
`bot.db.before-delivery-<timestamp>.bak`. Файловая блокировка запрещает второй
экземпляр бота на той же базе. Установка `PRAGMA user_version=4` и добавление
таблиц/индексов повторно применимы. Отдельная транзакция однократно переносит
владельца: приоритет имеет сохранённый `flags.owner_id`, затем переменная окружения.
Если у старой базы нет сохранённого owner_id и переменная также не задана,
запуск требует прежний `OWNER_TELEGRAM_ID`; перенос не помечается завершённым.
Старые `sent`, baseline, пропуски, ошибки и message_id сохраняются, pending с полным
payload остаются проверяемыми задачами владельца. Неопределённые/старые записи
не становятся новой массовой рассылкой. Сохранённый bot_id продолжает защищать
от запуска другого Telegram-бота на той же базе.

Диагностика выполняется только при остановленном основном процессе. Команды
внутри runtime-образа (через `docker compose run --rm --no-deps it-radar-bot ...`):

```bash
python -m app.main --delivery-status
python -m app.main --delivery-status --telegram-id 123456
python -m app.main --resolve-item tg_example:42 --telegram-id 123456 --resolution sent
python -m app.main --resolve-item tg_example:42 --telegram-id 123456 --resolution skip
```

Для ручного `--resolution retry` у `uncertain`/`legacy_review` необходимо сначала
проверить чат и добавить `--allow-duplicate-risk`: Telegram sendMessage не имеет
ключа идемпотентности. Повтор разрешён только активному подписчику. Без
`--telegram-id` разрешён лишь разбор прежних записей, ещё не имеющих персональных
доставок. Вывод диагностики содержит Telegram ID и предназначен только оператору.
Публичный `/status` показывает исключительно состояние вызвавшего пользователя.

Схема v3 добавляет таблицу `command_reply_limits`. Обновление v2 → v3 создаёт
резервную копию до изменения, сохраняет прежние подписки, доставленные события,
приостановленные задачи, ожидающие ответы и offset. Повторное открытие не создаёт
дополнительную миграционную копию. Если `user_version` выше 4, приложение завершает запуск ошибкой вместо изменения неподдерживаемой базы.

## Обновление работающего Docker-сервиса

Выполняйте команды из **существующего каталога Compose**, сохраняя прежнее имя
Compose project и named volume. Не запускайте второй экземпляр long polling.

1. Соберите новую версию: `docker compose build`. Сборка включает тесты на Python 3.12.
2. Остановите старый процесс: `docker compose stop` (grace period 60 секунд).
3. Сделайте внешнюю копию volume. Например, при существующем контейнере:

   ```bash
   mkdir -p backups
   chmod 700 backups
   docker compose cp it-radar-bot:/data/bot.db backups/bot.db.before-multiuser
   chmod 600 backups/bot.db.before-multiuser
   ```

   Команда предполагает прежний `DB_PATH=/data/bot.db`. При собственном пути
   используйте его. Копирование после штатной остановки согласованно для текущего
   SQLite journal mode. Сохраните также внешние архивы volume, если они применяются.
4. Оставьте прежний `OWNER_TELEGRAM_ID` для переноса старой подписки.
5. Запустите `docker compose up -d --no-build`; проверьте `docker compose logs --tail=100`.
6. Проверьте `/status` владельца и `/start` двух аккаунтов. Затем отключите одного
   через `/stop`: второй должен остаться подписанным. Реальная проверка отправки
   требует новой подходящей публикации после baseline, а не повтора архива.

Автоматическая резервная копия дополнительно остаётся в `/data` рядом с базой.
Не выполняйте `down -v`, не удаляйте БД и не копируйте старую базу поверх работающей.
Откат старого кода на новой базе не поддерживается: он может использовать устаревшую
глобальную очередь. Для отката остановите сервис и восстановите отдельно сохранённую
копию, учитывая потерю новых подписок/изменений после неё.

## Остановка и бюджет сбора (A03)

`SOURCE_TIMEOUT_SECONDS` (по умолчанию 600) задаёт общий кооперативный бюджет
одного источника: страницы, детали и обработка результата используют один deadline.
Он передаётся через Compose. Вложенные HTTP/collector-вызовы не начинают новый бюджет.
SIGTERM/SIGINT прерывают паузы; перед следующим запросом и фиксацией результата
проверяются отмена и deadline. Отмена не считается ошибкой источника; timeout
сохраняется как его ошибка и не останавливает другие источники. Неполный снимок
не устанавливает baseline и не продвигает курсор, в том числе после restart.

Отмена кооперативная: уже начатый `requests` не прерывается принудительно и ожидает
сетевого тайм-аута. Тайм-аут запроса уменьшается по оставшемуся бюджету; это не жёсткий
предел для DNS и сервера, непрерывно присылающего данные. Потоковое ограничение
загрузки (A08) остаётся отдельной задачей. Приложение не создаёт фоновых потоков
загрузки, которые могли бы продолжать работу после отмены.

Проверка A03: правила, 207 unittest-тестов и Docker build прошли; сценарии отмены
и timeout находятся в `tests/test_collection_cancel.py`.

## Изменённые публикации (A04, схема v4)

`seen_items.content_hash` вычисляется из исходного содержания, ссылок и структурированных
данных. `revision` увеличивается при изменении; `content_updated_at` отмечает время
наблюдения версии, а `first_seen_at` сохраняется. Вычисленные фильтрами категории,
статус и дедлайн не меняют хеш. Для исходного структурированного дедлайна используется
`Item.source_deadline`, отдельно от вычисляемого `deadline`.

Миграция v3 → v4 создаёт backup до изменения, заполняет хеши существующих payload и
`opportunity_at` исходной датой публикации. Она не пересматривает отклонённые записи
и не создаёт доставок сама по себе. История sent/message_id, курсоры, подписки,
лимиты ответов и ожидающие задачи сохраняются; повторная миграция не требуется.

Изменённое `rejected` (в том числе прежнее глобальное `expired`) проверяется заново. Если оно стало подходящим, новая граница
`opportunity_at`/`eligible_at` берётся из предыдущего полного снимка источника:
только активные до него подписчики допускаются к повторно открытому объявлению.
Точное время правки источником неизвестно, поэтому это намеренно осторожная граница
против отправки архива после подписки/паузы. Исходная дата публикации не подменяется;
проверка максимального возраста и актуальности остаётся действующей.

Неподходящая новая версия переводит оставшиеся `pending`/`suspended` в `expired`.
При повторном открытии могут восстановиться только такие безопасно истёкшие задачи,
для которых подписка всё ещё подходит по границам; попытки и retry deadline сохраняются.
`sent`, `sending`, `uncertain`, `failed` и `skipped` автоматически не повторяются.
Принятый baseline, legacy `sent`/`uncertain`/`failed`/`skipped`/`legacy_review` не превращаются в новую рассылку.
Правка всё ещё подходящего объявления обновляет содержание без расширения старой аудитории.
Ссылки для дедупликации обновляются; факт прежней отправки продолжает защищать от
копий события из других источников. Уникальная пара пользователь–item_key сохраняется.

Telegram включает уже известные сообщения последней страницы в проверку изменений,
не добавляя HTTP-запросов. История глубже этой страницы автоматически не пересматривается;
при обновлении курсора меньший ID из такой страницы никогда не сдвигает его назад.
Для сайтов проверяются изменения всех записей полного каталога. Повторный сезон
под тем же source ID не является новой сущностью: для повторного уведомления уже
получившего пользователя нужен отдельный идентификатор события, а не сброс истории.

Проверка A04: правила, 224 unittest-теста и Docker build прошли локально и в Python 3.12; новые сценарии
версий и безопасной рассылки находятся в `tests/test_item_revisions.py`.
