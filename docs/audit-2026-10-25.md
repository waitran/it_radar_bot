### B01 · P1 · Тело редиректа загружается до проверки ограничения A08

**Код:** [app/collectors/base.py:173](../app/collectors/base.py#L173),
[app/collectors/base.py:109](../app/collectors/base.py#L109).

`http_get()` вызывает высокоуровневый `requests.get(..., stream=True,
allow_redirects=False)`. В проверенных версиях Requests запрет перехода не
отключает подготовку следующего запроса: Session вызывает `resolve_redirects()`
для заполнения `Response.next`. Этот путь обращается к `response.content` и
вычитывает тело ответа 302 **до возврата из requests.get**.

К моменту входа в `_read_response()` лимит уже обойдён. Более того, для статуса
не 200 функция возвращает ответ без проверки его закешированного размера.
Переход по Location при этом не выполняется — проблема именно в загрузке тела.

**Воспроизведение:** настоящий Requests Session с подменённым транспортным
адаптером возвращает 302, Location и тело размером 1 МиБ. Вызов клиента с
`max_bytes=16` возвращает 302, а счётчик чтения показывает 1 048 576 байт.
Результат одинаков локально и в Docker с Requests 2.34.2. Сеть не используется.

**Риск:** ответ сайта или Telegram с большим либо медленным телом редиректа
обходит контроль памяти и проверки отмены между порциями. При достаточно большом
ответе возможно исчерпание памяти. Реальный OOM не воспроизводился.

**Исправление:** исключить внутреннее вычитывание redirect-тела Session до
прикладного контроля; отклонять редирект с немедленным закрытием соединения,
не загружая его тело. Нужен тест с настоящим Session/адаптером, а не только
с подменой `requests.get()`: нынешние моки обходят сам дефект.
Существующие тесты обычного ответа и gzip/deflate сохранить.

### B02 · P1 · Долгий сбор задерживает ответы всем пользователям

**Код:** [app/main.py:523](../app/main.py#L523),
[app/main.py:508](../app/main.py#L508).

`Bot.loop()` синхронно запускает полный `run_cycle()`. Планировщик вызывается
после обхода всех источников или в промежутках между полными обходами. Поток
long polling принимает команды и фиксирует подписки независимо, но сам ответы
не отправляет. Пока один сборщик ожидает сеть, очередь команд и готовые
уведомления не обслуживаются этим рабочим циклом.

**Воспроизведение:** один сборщик удерживается управляемым Event. Во время его
работы обработан `/start`: `is_active=true`, приветствие в pending, вызовов
отправки — 0. После освобождения сборщика появляется первый вызов отправки.
Не требуется ждать настоящего сетевого тайм-аута, чтобы подтвердить зависимость.

**Риск:** пользователь долго не видит приветствия или ответа `/status`; готовые
события исправных источников ждут другие источники. Кооперативный бюджет по
умолчанию — 600 секунд на источник, а не на весь цикл. В конфигурации 10
источников: сумма таких бюджетов — 100 минут, без гарантии жёсткого сетевого
предела из-за DNS/заголовков. Это расчёт, а не измеренная задержка production.

**Исправление:** обслуживать доставку независимо от полного сбора, сохранив один
канал отправки, долговечный claim, ограничения Telegram и блокировки изменений
подписок. Если сначала делать промежуточные отправки между источниками, отметить,
что они уменьшают задержку, но не устраняют её внутри одного долгого запроса.
Добавить проверку именно реального рабочего цикла, а не ручного параллельного
вызова `dispatch_pending()` из теста.

### B03 · P2 · Проверка правил перед отправкой не гарантирует свежесть источника

**Код:** [app/main.py:371](../app/main.py#L371),
[app/main.py:307](../app/main.py#L307).

`drain_pending()` сначала берёт объект из `_fresh_items`. Telegram перечитывается
только при отсутствии объекта; время последней проверки конкретной публикации
не хранится. Объекты сайтов также используются до следующего общего сбора.
`Filters.check()` проверяет сохранённый текст и сроки, но не узнает о закрытии,
удалении или изменении публикации на сайте после снимка.

**Воспроизведение:** в кеше сохранено открытое событие, источник для повторного
чтения моделируется закрытым. Через 30 минут `drain_pending()` отправляет событие:
`sent=1`, `fetch_post` не вызывается (`refresh_calls=0`). Проверка выполняется без
реального ожидания, через параметр `now`.

**Риск:** при очереди на несколько минут или часов пользователи могут получить
уже закрытые возможности. При штатном часовом опросе кеш обычно обновляется
следующим сбором; отдельная проверка допускает источник возрастом до двух
интервалов. Это ограничение не эквивалентно обещанию README о повторной проверке
актуальности непосредственно перед отправкой.

**Исправление:** определить и документировать допустимый возраст подтверждения,
хранить `verified_at` по событию, обновлять просроченную проверку до очередной
отправки. Делить один свежий результат проверки между получателями одного
события, чтобы не загружать источник отдельно для каждого пользователя.
Если проверка недоступна, приостанавливать доставку, сохраняя историю.

### B04 · P2 · `--check-config` пропускает неверный тип category.label

**Код:** [app/config.py:143](../app/config.py#L143),
[app/formatting.py:39](../app/formatting.py#L39),
[app/main.py:312](../app/main.py#L312).

Для категории проверяются структура и keywords, но `label` сохраняется без
проверки типа. Форматирование ожидает строки в `', '.join(labels)`.

**Воспроизведение:** в копии YAML задать `rules.categories.internships.label:
[invalid]`. `Config.load()` и `validate_runtime()` проходят; реальный CLI
`--check-config` заканчивается с кодом 0. Стажировка проходит фильтр, но
`format_message()` вызывает `TypeError`.

**Риск:** ошибка настроек обнаруживается при рассылке, а не при проверке запуска.
Исключение возникает до claim: задача остаётся в очереди, и обработка подходящих
событий этой категории продолжает падать. Подтверждён сценарий с некорректным
пользовательским YAML; стандартный config.yaml этим дефектом не затронут.

**Исправление:** проверять `label` как непустую строку при загрузке Config и
выдавать `ConfigurationError` с именем поля. Добавить случаи list/null/int
и корректного Unicode-названия категории.

### B05 · P2 · Изменение разметки пагинации может привести к пропуску истории

**Код:** [app/collectors/telegram_channel.py:130](../app/collectors/telegram_channel.py#L130),
[app/collectors/telegram_channel.py:200](../app/collectors/telegram_channel.py#L200),
[app/main.py:470](../app/main.py#L470).

Парсер ищет ссылки только через `a.tme_messages_more`. Если публикации по-прежнему
распознаются, а CSS-класс ссылки на старую историю изменился, `next_before=None`.
`fetch_channel()` принимает это за конец истории даже при `oldest > since_id`.
Вызывающий код после такой выдачи сохраняет новый максимальный ID.

**Воспроизведение:** сохранён cursor=1; страница содержит посты 100 и 101 и ссылку
`/s/example?before=100` с `data-before=100`, но классом `changed-pagination`.
Загрузка выполняется один раз, возвращаются только 100–101. В отдельном проходе
`Bot.run_cycle()` сохраняет cursor=101. При наличии публикаций 2–99 на старых
страницах они больше не будут запрошены обычным проходом.

**Риск:** при частичном изменении внешней разметки события могут быть пропущены
без ошибки источника. Это искусственная модель изменения разметки; утверждения,
что Telegram сейчас изменил этот класс, в отчёте нет.

**Исправление:** отличать доказанный конец истории от исчезновения ожидаемой
пагинации. Если сохранённая граница не достигнута и полнота не подтверждена,
сохранять ошибку источника и прежний курсор. Не превращать это в бесконечную
блокировку при действительно удалённой старой истории: необходима явная политика
такого восстановления с тестами обоих вариантов.

Для повторения Docker-probe из корня репозитория:


Имя runtime-образа приведено для текущего Compose-проекта. При другом имени
каталога сборки подставьте имя своего образа. Не подключайте рабочий volume:
probe использует временные SQLite-базы внутри собственного процесса.
