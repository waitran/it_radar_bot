# Этап 5: состояние и доставка

Реальная рассылка и запуск с пользовательским токеном на этом этапе не выполнялись.
Поведение Telegram проверено подменой HTTP, состояние — настоящими временными
SQLite-базами. Команды ручного разбора очереди также проверены отдельными процессами.

## Хранение и миграция

При первом открытии старой БД создаётся резервная копия
`<DB_PATH>.before-delivery-<timestamp>.bak` через SQLite Backup API, с правами 0600.
Затем добавляются поля очереди и таблица идентификаторов дублей. Исходные записи,
флаги, ID каналов и отметки исходных точек сохраняются. БД не пересоздаётся.
Для нового пустого файла резервная копия не нужна; повторный запуск уже обновлённой
схемы не создаёт новые копии. Копии содержат данные БД: храните их локально.

Публикация сохраняется полностью: исходный текст, даты, ссылки, категории, тип
вакансии, опыт и явное закрытие. Старые записи без полного контекста и отметки
доставки переводятся в `legacy_review`; автоматически они не отправляются.
Старые подтверждённые/исходные записи сохраняют соответствующий статус.

Один процесс удерживает файловую блокировку `<DB_PATH>.lock` до закрытия SQLite.
Второй процесс с тем же путём не запускается. БД привязывается к ID владельца,
а после `getMe` — к ID бота. Для другого владельца/бота нужен отдельный файл.
Секретный Telegram-токен в SQLite не записывается. Целевая среда блокировки — Linux.

## Состояния очереди

| Состояние | Значение |
|---|---|
| `pending` | Ожидает отправки; `available_at` задаёт время следующей допустимой попытки |
| `sending` | Попытка записана в БД до HTTP-запроса |
| `sent` | Telegram подтвердил отправку; сохранён `message_id` |
| `uncertain` | Результат неизвестен; автоматического повторения нет |
| `failed` | Явный отказ Telegram, например 400/401/403 |
| `expired` | Повторный отбор не пройден или публикация исчезла |
| `skipped` | Пауза, отключённый источник, неподтверждённый РТК ИТ или дубль |
| `baseline` | Принятая запись исходного снимка, без отправки |
| `rejected` | Отклонено правилами |
| `legacy_review` | Старая очередь без надёжного контекста/результата; нужен ручной разбор |

При перезапуске незавершённые `sending` становятся `uncertain`. Так не возникает
слепого повтора после сбоя между принятием сообщения Telegram и записью результата
в SQLite. Гарантии «ровно один раз» при неизвестном сетевом результате нет: выбран
режим без автоматического дубля, с возможным ручным восстановлением пропущенной
доставки. Поведение API описано в [Telegram Bot API](https://core.telegram.org/bots/api#sendmessage).

## Проверка перед отправкой и повторы

Сначала проверяются источники, затем очередь. При недоступном источнике его
уведомления ожидают успешной проверки. Удалённые из конфигурации источники и
неподтверждённый РТК ИТ не отправляются. Снимок старше двух интервалов опроса не
используется для доставки.

Вакансия должна присутствовать в текущем полном каталоге сайта. Telegram-пост из
старой очереди перечитывается через публичный `t.me/s/<username>?before=<id+1>`.
Если он удалён или закрыт, уведомление не отправляется. Использование сохранённого
снимка между проверками не гарантирует обнаружения изменения источника раньше
следующего опроса; даты и правила повторно проверяются перед каждой попыткой.

- Успешный ответ сохраняет `message_id`; запись повторно не отправляется.
- `429` переносит всю очередь на `retry_after`, отсчитываемый после ответа сервера.
- `ConnectTimeout` откладывает попытку с увеличивающейся паузой, до часа.
- `ReadTimeout`, потеря соединения, неразбираемый ответ и 5xx дают `uncertain`.
- `400` — явная ошибка записи; `403` выключает уведомления; `401` завершает процесс.
- Между отправками выдерживается пауза. Между циклами сбора очередь проверяется
  каждые две секунды, а источники — по `POLL_INTERVAL_SECONDS`. Сам сбор может
  задержать очередную попытку; после него для короткого retry не нужно ждать час.

HTML и ссылки экранируются; небезопасные URL исключаются. Размер готового HTML
ограничен с учётом UTF-16, теги и URL не разрезаются.

## Команды, пауза и перезапуск

Принимаются только точные `/start`, `/stop`, `/status`, `/help` от заданного
владельца в личном чате. Проверяются и `chat.id`, и `from.id`. Суффикс `@username`
должен соответствовать текущему боту. Редактирование старого сообщения не является
новой командой. Состояние команды и offset сохраняются одной транзакцией до ответа;
потерянное подтверждение не приводит к повторному исполнению старого `/start`.

`/stop` выключает отправку и переводит ожидающие записи в `skipped`. Источники
продолжают проверяться. После `/start` инициируется проверка; первый успешный снимок
каждого источника после паузы сохраняется без отправки. Это предотвращает рассылку
истории, появившейся между проверками во время паузы. При таком консервативном режиме
публикации, появившиеся между возобновлением и этим снимком, тоже могут быть пропущены.

Команда остановки и отправка синхронизированы: после обработки `/stop` новые
запросы уведомлений не начинаются. Уже начатый HTTP-запрос нельзя отозвать; его
результат сохраняется, а следующая отправка блокируется. Завершение процесса также
не отзывает запрос, уже принятый Telegram.

При старте проверяются `getMe` и отсутствие webhook. Webhook не удаляется автоматически.
Конфликт polling (`409`) и ошибка авторизации (`401`) завершают процесс с явной ошибкой.
`/status` показывает ошибки источников и числа pending/uncertain/failed/legacy_review.
Служебные ответы не образуют отдельную очередь: при недоступности API ответ может
не дойти, но применённая команда и offset остаются сохранёнными.

## Дубли

ID внутри источника остаются постоянными. Для перепечаток используются нормализованные
конкретные URL оригинала/заявки: убираются якоря и известные tracking-параметры.
Одинаковый полный текст дополнительно сравнивается внутри одного источника.
Период такого сопоставления — 30 дней; разные известные дедлайны не склеиваются.

Одинаковый заголовок у разных компаний больше не считается достаточным доказательством
дубля. Общие главные страницы не используются как идентификатор. Перепечатка с другой
ссылкой/текстом может прийти повторно: универсальное семантическое сравнение не выполняется.
Отклонённая или окончательно пропущенная запись не блокирует новое подходящее объявление.

## Ручной разбор без рассылки

Сначала остановите процесс бота, чтобы освободить блокировку БД. Для локальной установки
из корня проекта с правильным `DB_PATH`:

```bash
python -m app.main --delivery-status
```

Команда показывает счётчики и ключи записей, требующих разбора. Она не использует
сеть и не требует Telegram-токен. При открытии старой схемы выполняется описанная
миграция с резервной копией.

После проверки переписки выберите действие для конкретного ключа (пример ключа
ниже нужно заменить реальным из отчёта):

```bash
# Подтвердить, что сообщение уже пришло:
python -m app.main --resolve-item tg_example:123 --resolution sent

# Отказаться от отправки, сохранив запись:
python -m app.main --resolve-item tg_example:123 --resolution skip

# Повтор неизвестной/старой доставки может дать дубль — только осознанно:
python -m app.main --resolve-item tg_example:123 --resolution retry --allow-duplicate-risk
```

Разрешён разбор состояний `uncertain`, `failed`, `legacy_review`. Для повтора
`uncertain`/`legacy_review` требуется явный флаг риска. Эти команды только изменяют
состояние; отправка возможна после обычного запуска, успешного чтения источника
и повторной фильтрации. Известные отправленные записи нельзя повторить этой командой.

При Docker-установке используйте тот же named volume, предварительно остановив сервис:

```bash
docker compose stop
docker compose run --rm --no-deps --build it-radar-bot python -m app.main --delivery-status
```

Для действий разбора замените `--delivery-status` нужными аргументами. Compose по-прежнему
требует локальный `.env`, хотя сам режим диагностики не обращается к Telegram.
Не удаляйте named volume или резервную копию. Не редактируйте очередь SQL-командами
при запущенном боте и не откатывайте код к старой схеме без плана восстановления.

## Проверки этапа

Добавлены 43 теста: миграция, резервная копия, сохранение payload, блокировка,
привязка владельца/бота, неизвестный результат и сбой после начала отправки,
429 и backoff, истечение срока, изменение правил, удаление публикации,
источник с ошибкой, перезапуск, `/stop` во время сбора и отправки, возобновление
без архива, защита команд, offset, webhook/409, дедупликация, безопасный HTML
и CLI ручного разбора.

```bash
python -m unittest tests.test_delivery -v
python -m unittest discover -s tests -v
python -m tests.test_rules
docker build -t it-radar-bot:stage5 .
```

Реальная отправка владельцу, запуск с новым локально сохранённым токеном и
проверка работы сервиса целиком остаются этапом 6. Компрометированные токены
из переписки и старого кода не использовались.

Дополнительно 23 октября 2026 года проверено реальное повторное чтение
`mgtsstudents/16` через публичную страницу истории: получены дата и 1082 символа
текста. Выявленная ссылка `data-after` на более новые сообщения теперь корректно
проверяется без перехода по ней. Отправок сообщений при этой проверке не было.
После изменения `config.yaml` перезапустите процесс: горячая перезагрузка правил
не выполняется.
