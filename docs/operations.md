# Эксплуатация и восстановление

## Резервные копии

В Compose `BACKUP_DIR=/backups` связан с каталогом хоста
`BACKUP_HOST_PATH` (по умолчанию `./backups`). Этот каталог находится вне volume
`bot-data`, поэтому удаление volume базы не удаляет копии. Это не защита от потери
всего компьютера: настройте отдельную отправку каталога на другое устройство или
в ваше внешнее хранилище. Адрес и учётные данные такого хранилища бот не запрашивает.

При работающем боте отдельный поток сразу создаёт первую копию, затем повторяет
операцию через `BACKUP_INTERVAL_SECONDS` (по умолчанию 86400). Сохраняются
`BACKUP_KEEP` завершённых копий (по умолчанию 7, минимум 2). Ошибка вызывает паузу
до следующей попытки, но не останавливает обработку подписок. `last_backup_at`
фиксируется в SQLite только после успешного завершения.

Используется SQLite Backup API с отдельным read-only соединением; данные WAL
попадают в копию без остановки сервиса. Перед публикацией выполняется quick_check
и проверка таблиц/версии. Файл создаётся с правами 0600 как `.part`, затем атомарно
переименовывается. Незавершённые файлы не считаются копиями и удаляются при ошибке
текущей операции. При отмене или исчерпании бюджета копирования предыдущие копии
сохраняются. Чужие файлы и страховые копии перед восстановлением ротация не удаляет.

Для локального Python резервирование включается непустым `BACKUP_DIR`; он должен
быть вне каталога DB_PATH. В Compose каталог задан явно. Пример ручной копии:

```bash
docker compose exec it-radar-bot python -m app.backup create \
  --db /data/bot.db --dir /backups --keep 7
```

Команда печатает имя файла и общие счётчики, без Telegram ID и токенов.

## Проверка и восстановление

Замените `FILE.sqlite3` именем выбранной завершённой копии:

```bash
docker compose run --rm --no-deps it-radar-bot \
  python -m app.backup verify /backups/FILE.sqlite3
```

Восстановление сначала проверяет копию. Блокировка целевой базы запрещает замену,
пока с ней работает бот. Для существующего файла обязательны `--replace` и
`--safety-dir`: перед заменой будет создана отдельная проверенная копия прежнего
состояния `it-radar-before-restore-*.sqlite3`. Она не входит в обычную ротацию.
Запись выполняется через SQLite Backup API, включая корректную работу с журналом,
а не простым копированием одного файла поверх SQLite/WAL.

```bash
docker compose stop it-radar-bot
docker compose run --rm --no-deps it-radar-bot \
  python -m app.backup restore /backups/FILE.sqlite3 \
  --target /data/bot.db --replace --safety-dir /backups
docker compose up -d
```

Для пробного восстановления без замены рабочей базы используйте незанятый путь:

```bash
docker compose run --rm --no-deps it-radar-bot \
  python -m app.backup restore /backups/FILE.sqlite3 --target /data/restore-check.db
```

История соответствует моменту выбранной копии: сообщения, отправленные **после**
неё, в этой истории отсутствуют. Автоматически повторять их после восстановления
опасно. Поэтому восстановление переводит незавершённые задачи в `legacy_review`,
сбрасывает незавершённый fan-out и устанавливает активным подпискам новую границу
рассылки на момент восстановления. Архив после снимка автоматически не рассылается.
Подписчики остаются активными и получают последующие события; старые задачи
разбираются оператором по Telegram и диагностике доставок. Для старой базы без
таблицы users рассылка владельцу остаётся выключенной до явной активации. Таким образом, резервная копия не обеспечивает exactly-once между моментом
снимка и аварией. Страховая копия позволяет изучить более новое состояние, если
оно сохранилось. Не удаляйте volume и не сбрасывайте историю дедупликации.

Тесты резервирования проверяют живую базу, WAL, подписчиков, polling offset,
отправленные доставки с attempts/message_id, отмену, ротацию, ошибку копирования,
запрет восстановления поверх работающего бота и страховую копию перед заменой.
