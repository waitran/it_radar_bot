# Эксплуатация и восстановление

## Резервные копии

В Compose `BACKUP_DIR=/backups` связан с каталогом хоста
`BACKUP_HOST_PATH` (по умолчанию `./backups`). Этот каталог находится вне volume
`bot-data`, поэтому удаление volume базы не удаляет копии. Это не защита от потери
всего компьютера: настройте отдельную отправку каталога на другое устройство или
в ваше внешнее хранилище. Адрес и учётные данные такого хранилища бот не запрашивает.

При работающем боте отдельный поток сразу создаёт первую копию, затем повторяет
операцию через `BACKUP_INTERVAL_SECONDS` (по умолчанию 86400). Сохраняются
`BACKUP_KEEP` завершённых копий (по умолчанию 7, минимум 2). Ошибка вызывает паузу
до следующей попытки, но не останавливает обработку подписок. `last_backup_at`
фиксируется в SQLite только после успешного завершения.

Используется SQLite Backup API с отдельным read-only соединением; данные WAL
попадают в копию без остановки сервиса. Перед публикацией выполняется quick_check
и проверка таблиц/версии. Файл создаётся с правами 0600 как `.part`, затем атомарно
переименовывается. Незавершённые файлы не считаются копиями и удаляются при ошибке
текущей операции. При отмене или исчерпании бюджета копирования предыдущие копии
сохраняются. Чужие файлы и страховые копии перед восстановлением ротация не удаляет.

Для локального Python резервирование включается непустым `BACKUP_DIR`; он должен
быть вне каталога DB_PATH. В Compose каталог задан явно. Пример ручной копии:

```bash
docker compose exec it-radar-bot python -m app.backup create \
  --db /data/bot.db --dir /backups --keep 7
```

Команда печатает имя файла и общие счётчики, без Telegram ID и токенов.

## Проверка и восстановление

Замените `FILE.sqlite3` именем выбранной завершённой копии:

```bash
docker compose run --rm --no-deps it-radar-bot \
  python -m app.backup verify /backups/FILE.sqlite3
```

Восстановление сначала проверяет копию. Блокировка целевой базы запрещает замену,
пока с ней работает бот. Для существующего файла обязательны `--replace` и
`--safety-dir`: перед заменой будет создана отдельная проверенная копия прежнего
состояния `it-radar-before-restore-*.sqlite3`. Она не входит в обычную ротацию.
Запись выполняется через SQLite Backup API, включая корректную работу с журналом,
а не простым копированием одного файла поверх SQLite/WAL.

```bash
docker compose stop it-radar-bot
docker compose run --rm --no-deps it-radar-bot \
  python -m app.backup restore /backups/FILE.sqlite3 \
  --target /data/bot.db --replace --safety-dir /backups
docker compose up -d
```

Для пробного восстановления без замены рабочей базы используйте незанятый путь:

```bash
docker compose run --rm --no-deps it-radar-bot \
  python -m app.backup restore /backups/FILE.sqlite3 --target /data/restore-check.db
```

История соответствует моменту выбранной копии: сообщения, отправленные **после**
неё, в этой истории отсутствуют. Автоматически повторять их после восстановления
опасно. Поэтому восстановление переводит незавершённые задачи в `legacy_review`,
сбрасывает незавершённый fan-out и устанавливает активным подпискам новую границу
рассылки на момент восстановления. Архив после снимка автоматически не рассылается.
Подписчики остаются активными и получают последующие события; старые задачи
разбираются оператором по Telegram и диагностике доставок. Для старой базы без
таблицы users рассылка владельцу остаётся выключенной до явной активации. Таким образом, резервная копия не обеспечивает exactly-once между моментом
снимка и аварией. Страховая копия позволяет изучить более новое состояние, если
оно сохранилось. Не удаляйте volume и не сбрасывайте историю дедупликации.

Тесты резервирования проверяют живую базу, WAL, подписчиков, polling offset,
отправленные доставки с attempts/message_id, отмену, ротацию, ошибку копирования,
запрет восстановления поверх работающего бота и страховую копию перед заменой.

## Контроль прогресса

Compose запускает `python -m app.healthcheck` каждые 30 секунд. Команда читает
атомарный файл `/data/bot.health.json` и не открывает SQLite, не получает
Telegram updates и не создаёт второй экземпляр бота. Файл имеет права 0600;
содержит только агрегированные счётчики и времена, без ID подписчиков и токенов.
Основной цикл обновляет его примерно каждые 10 секунд.

Нездоровыми считаются: отсутствие heartbeat/прогресса планировщика более 90 секунд,
зависший polling (с учётом объявленного retry_after), выход работы источника за
его бюджет с сетевым запасом, ошибка полного цикла, отсутствие успешных источников
в завершённом обходе, слишком старая активная очередь и сбои/пропуск резервирования.
Один отказавший источник при наличии успешных не объявляет весь бот неисправным.
Для начальной копии предусмотрен запас 120 секунд. Возраст очереди считается по
времени eligibility события, с fallback на first_seen для legacy; при повторном
открытии старая дата первого обнаружения не вызывает ложную тревогу.

`MAX_QUEUE_AGE_SECONDS` по умолчанию 86400. Подберите его с учётом числа получателей,
интервала сбора и общей пропускной способности Telegram.

```bash
docker compose ps
docker compose exec it-radar-bot python -m app.healthcheck
docker compose exec it-radar-bot cat /data/bot.health.json
```

Docker отмечает контейнер как unhealthy после трёх неудачных проверок; стартовый
запас — 90 секунд. Статус unhealthy сам по себе не вызывает перезапуск по
`restart: unless-stopped`: настройте наблюдение за Docker health events в вашем
хостовом мониторинге и канал оповещения оператора. Бот не отправляет неожиданных
операционных сообщений подписчикам и не требует для проверки токена или сети.

## Ресурсы и хранение истории

Compose ограничивает память бота 512 МиБ, CPU — одним ядром, число процессов/потоков —
128. Значения изменяются через `BOT_MEMORY_LIMIT`, `BOT_CPU_LIMIT`, `BOT_PIDS_LIMIT`.
Логи Docker используют json-file с max-size=10m и max-file=3. Остановка даёт
кооперативным сетевым операциям до 90 секунд; DNS/заголовки не обещают жёсткого
deadline, а при прерывании отправки долговечный claim восстанавливается как uncertain.

Healthcheck проверяет свободное место для SQLite и каталога резервирования.
`MIN_FREE_DISK_MB` по умолчанию 1024; значение 0 отключает этот порог. При низком
остатке выдаётся `disk_space_low`, без удаления данных. История событий, ключи
дедупликации и персональные терминальные доставки намеренно сохраняются. Для
неограниченного срока хранения нужно планировать дисковый объём: автоматическое
удаление истории нарушило бы защиту от повторной рассылки.

Реальное применение лимитов проверено в изолированном Docker-контейнере:
memory.max=536870912, pids.max=128, cpu.max=100000/100000; параметры ротации также
проверены через HostConfig. Рабочий volume при этой проверке не подключался.


## Непривилегированный runtime и старые volumes

Образ по умолчанию использует `USER 10001:10001`. Основной сервис имеет read-only
корневую ФС, tmpfs /tmp на 64 МиБ, cap_drop=ALL и no-new-privileges. Записываются
только SQLite/heartbeat в /data и копии в /backups. DB и lock-файл создаются с 0600.

Compose перед запуском бота выполняет одноразовый `storage-init`: без сети, без
Telegram-токена, с тремя capabilities только для смены владельца и прав. Он
подготавливает существующие /data и /backups для BOT_UID/BOT_GID, не изменяя
содержимое файлов. Ссылки и нештатные типы файлов не обходятся: используются
дескрипторы с O_NOFOLLOW, hardlinks отклоняются. Успешное завершение init является
условием запуска основного сервиса. Это не дополнительная база или фоновый worker.

При первом переходе со старой root-версии используйте порядок из README:
соберите образ, остановите старый сервис, скопируйте весь /data в upgrade-backups,
затем выполните `docker compose up -d --no-build`. Каталоги состояния получают 0700,
файлы — 0600. Для доступа к host-backups без sudo можно заранее выбрать UID/GID
своего пользователя хоста; они должны быть положительными, не root.

В изолированном Docker-тесте старые root-owned файлы подготовлены init-контейнером
с указанными capabilities; runtime UID=10001 сохранил пользователя, polling offset
и sent/message_id, создал новую копию и выполнил healthcheck. Проверены CapEff=0,
NoNewPrivs=1 и отказ записи в код приложения. Рабочие volumes не использовались.


## CI

`.github/workflows/ci.yml` выполняется на push, pull request и вручную через
workflow_dispatch. Права GITHUB_TOKEN ограничены contents:read; checkout закреплён
на SHA официального actions/checkout v6 и не сохраняет credentials в git config.
Параллельный устаревший запуск одной ветки отменяется.

Проверяются отслеживаемые Git файлы на известные форматы Telegram/GitHub токенов,
приватные ключи, dotenv и файлы состояния. Диагностика содержит только пути,
не найденные значения. Это дополнительные правила защиты, а не доказательство
отсутствия любых секретов. Затем проверяются Python-синтаксис, Compose, pip check,
правила и unittest в Docker; тесты отдельно повторяются с --network none.
Проверяется непривилегированный runtime. Для аудита зафиксированных зависимостей
используется pip-audit 2.9.0 в отдельном временном окружении внутри контейнера;
проектные зависимости не изменяются. Обращение к базе известных уязвимостей
требует сети, настоящие Telegram credentials для CI не нужны.

Локально выполнены все 337 тестов, Docker-сборка и повтор 337 тестов без сети.
Отдельная сборка dependencies с --pull --no-cache подтвердила установку lock-файла
из PyPI и успешный pip check. pip-audit не нашёл известных уязвимостей на момент
проверки; новые advisories могут изменить результат последующих запусков.
Актуальный результат удалённого workflow смотрите в GitHub Actions.

CI не публикует образ и не обновляет рабочий бот. Внешний/offsite backup и канал
уведомления хостового мониторинга настраиваются оператором отдельно.
