# Персональные функции и обновление до v7

Реализация подготовлена в отдельной папке `it_radar_bot` из снимка репозитория
`waitran/it_radar_bot`, commit `62011c84ba0f583b74f535958c38406ab9906e49`.
Исходная рабочая папка содержала другой проект `opportunity_bot`; его файлы не менялись.
Git-копия здесь имеет локальный базовый коммит снимка и ветку `codex/personal-features`;
это не клон с историей upstream. Для переноса используйте изменения относительно
первого локального коммита, а не замену рабочей базы или `.env`.

## Команды и проверка с тестовым ботом

1. `/start`: включить подписку. Первоначальная история источников не рассылается.
2. `/settings`: выбрать категории, направления и формат кнопками. Направления
   выбираются независимо; «Все направления» снимает ограничения. Кнопки «Город»
   и «Часовой пояс» предлагают отправить текст следующим сообщением. «любой»
   сбрасывает город; часовой пояс задаётся именем IANA (`Europe/Moscow`, `Asia/Tokyo`).
   Повторное нажатие той же кнопки устанавливает то же значение.
3. На новом подходящем уведомлении нажать `⭐ Сохранить` дважды, открыть `/saved`:
   должна появиться одна запись. Сохранение также доступно из `/week`.
4. `/saved`: открыть оригинал, перелистывать страницы, удалить запись,
   включить «За 3 дня» и/или «За 1 день». Для напоминания нужны сохранённое
   событие, включённая подписка и достоверный будущий дедлайн. Если время
   напоминания уже прошло, новое задание не создаётся.
5. `/week`: проверить сортировку и фильтры; показывает сегодня и следующие шесть
   календарных дней в часовом поясе пользователя. События с известным временем,
   которое уже прошло, исключаются. Для даты без времени событие остаётся
   до конца календарного дня; точное время ему не приписывается.
6. `/reminders`: просмотреть запланированные задания и отменить нужное кнопкой.
   Перезапуск контейнера сохраняет задания. Удаление из избранного и `/stop`
   отменяют ожидающие напоминания. `/start` не восстанавливает отменённые задания:
   включите их явно из `/saved`.
7. На втором тестовом аккаунте установить другие фильтры: избранное и настройки
   должны отличаться. Поддельные callbacks с чужим ID не изменяют его данные.
8. `/status`, `/help` и административный `/check` сохраняют прежнюю роль.
   `/check` не появляется в публичном меню и доступен только владельцу.

Для быстрой ручной проверки напоминания используйте отдельный тестовый бот,
отдельную SQLite-базу и тестовый источник с дедлайном через 1 или 3 дня.
Проверьте доставку в 09:00 выбранного часового пояса. Не меняйте сроки в рабочей БД.
Автотесты проверяют эти интервалы без ожидания и без реального Telegram API.

## Гарантии и модель данных

- Старые пользовательские настройки по умолчанию: все четыре категории,
  все направления, любой формат и город; часовой пояс `Europe/Moscow`.
  Пользовательский часовой пояс меняет афишу и календарные напоминания, но не
  глобальную интерпретацию дат источника (`rules.timezone` из конфигурации).
- Персональная релевантность проверяется при fanout и непосредственно перед
  устойчивым claim отправки. Настройки не перезапускают fanout и не перечитывают
  архив для рассылки. Существующая граница подписки/возобновления сохранена.
- SQLite v7 добавляет `user_preferences`, `item_refs`, `event_metadata`,
  `saved_items`, `reminder_jobs` и `command_replies.reply_markup`.
  Короткий числовой `item_refs.id` используется в callback вместо URL.
  Индексы поддерживают диапазон дат/дней афиши, избранное и очередь напоминаний.
- Миграция использует существующую резервную копию `*.before-delivery-*.bak`
  перед изменением старой файловой базы; DDL/индексация/версия v7 фиксируются
  одной транзакцией существующего механизма миграций. Повторный запуск безопасен.
  Однократная индексация существующих payload не создаёт персональных доставок.
  Пользователи, история, дедупликация, курсоры и polling offset сохраняются.
- Напоминания используют тот же `_send_lock`, `_transmit` и глобальный
  `send_after`, что обычные уведомления и ответы. Когда все три вида готовы,
  слоты чередуются: команда → публикация → напоминание. Если один вид пуст,
  остальные используют свободные слоты. Ответы сохраняют ограничение на чат.
- `sending` после аварийного перезапуска становится `uncertain`; автоматического
  повтора нет. Успешные и неопределённые receipts сохраняются даже после
  удаления/повторного сохранения события. 429 откладывает общую отправку на
  `retry_after`; 403 деактивирует только соответствующего пользователя.
- Удаление, `/stop` и изменение настроек не могут отозвать HTTP-запрос, для
  которого уже зафиксирован claim. При безопасном retry повторно проверяются
  подписка, её epoch, избранное, дедлайн и закрытие регистрации.
- `answerCallbackQuery` выполняется до обработки состояния, вне блокировок БД
  и бота. Остальные ответы с клавиатурой проходят устойчивую очередь команд;
  новый запрос того же пользователя заменяет его предыдущую ожидающую страницу.

## Консервативное извлечение и ограничения

Даты извлекаются существующим `date_evidence`. Для индекса подходят только
однозначная дата проведения и отдельно однозначный дедлайн. Неоднозначные
несколько дат/сокращённые интервалы не получают вымышленную дату. Год без
явного указания привязан к дате публикации; без публикации нужен явный год.
Относительные даты требуют времени публикации. Время интерпретируется в
`rules.timezone`; дата без времени имеет отдельный признак точности. Для
структурированного `source_deadline` сохраняется точное время; legacy
`item.deadline` без происхождения не используется для создания напоминания.

Для дедлайна без времени напоминание назначается на 09:00 в пользовательском
часовом поясе за 1/3 календарных дня (с учётом DST); для точного времени —
за 24/72 часа. При новой собранной редакции будущие pending-задания пересчитываются.
После восстановления резервного снимка ожидающие напоминания переводятся
в `uncertain`: доставка после момента снимка неизвестна.
Задания с `sent`/`uncertain` сами не возобновляются после редактирования срока.
Если дата стала неизвестной, регистрация закрылась или дедлайн истёк,
ожидающее напоминание отменяется.

Направления определяются только по явным ключевым словам; формат — по
«онлайн»/«офлайн»/дистанционному/очному участию, город — по явным полям
`Город:`, `г.`, `Место проведения:`. При неизвестном признаке событие не
проходит установленное ограничение, но проходит отсутствие ограничения.
Сложная естественная речь может потребовать ручного уточнения публикации.
Без нового обхода источников актуальность регистрации перед напоминанием
не гарантируется: его текст всегда предлагает проверить оригинал и не
утверждает, что регистрация открыта. Известное закрытие блокирует отправку.

Афиша использует существующую базу, без сетевого обхода на команду. В SQL
выбираются только нужные даты, персональная релевантность применяется до
`LIMIT 4/OFFSET` (три карточки и индикатор следующей страницы). Ранее принятые
baseline-события видны без рассылки. Старые строки без исходного payload
не получают искусственных метаданных. Страницы ограничены 10 000, текст
экранируется; длинный URL оригинала переносится в URL-кнопку.

Первое обновление большой базы может занять время на индексацию всех имеющихся
payload. Сделайте резервную копию и предусмотрите окно остановки. При изменении
глобального часового пояса уже извлечённые метаданные не переинтерпретируются
сами: настройку источников следует сохранять при обновлении.

## Безопасное обновление существующего экземпляра

Выполняется оператором; реализация не делала деплой, push и не меняла `.env`.

1. Подготовить изменения на отдельной ветке относительно указанного upstream
   snapshot; проверить конфликтующие изменения, если рабочая версия новее.
2. Выполнить `python -m unittest discover -s tests -v` и `docker compose build`
   в каталоге IT Radar Bot. Для одной сборки без `.env` допустим исключительно
   фиктивный параметр `TELEGRAM_BOT_TOKEN=build-only-placeholder`: это не запускает
   бота. Для запуска оставьте свой прежний токен и owner ID.
3. Остановить прежний процесс `docker compose stop it-radar-bot`.
   Не применять `docker compose down -v` и не удалять volume.
4. Скопировать SQLite через штатный backup CLI старого/нового образа:
   `docker compose run --rm --no-deps it-radar-bot python -m app.backup create --db /data/bot.db --dir /backups`.
   Проверить полученный файл: `python -m app.backup verify /backups/<имя>.sqlite3`
   внутри контейнера. Сохранить отдельно прежний образ и конфигурацию.
5. Запустить новую версию с прежними volume, `.env`, OWNER_TELEGRAM_ID и
   конфигурацией: `docker compose up -d`. Миграция выполняется при открытии БД;
   её дополнительный pre-migration backup останется рядом с базой в volume.
6. Проверить логи, healthcheck, `/status`, `/settings`, `/saved`, `/week`,
   `/reminders` и отсутствие повторной рассылки. Сначала провести полный
   сценарий на отдельном тестовом аккаунте/боте и копии базы.
7. Для отката остановить новый процесс и восстановить проверенную копию v6
   штатным restore CLI с `--replace --safety-dir`, сохранив текущее состояние
   для разбора, затем вернуть прежний образ. Старое приложение не сможет
   открыть v7. Учесть, что восстановление снимка откатывает offset/историю
   после момента копирования и требует проверки последних доставок вручную.
